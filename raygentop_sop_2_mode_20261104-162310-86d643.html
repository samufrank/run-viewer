Why this grouping (and why no chaining)

In the original, r is visible 2 clock edges after the module inputs: edge k loads ul/vl/wl/rul/rvl/rwl, edge k+1 loads i1r/i2r/i3r from those registers (non-blocking, so the products use the values loaded at edge k), and assign r = i1r+i2r+i3r is combinational after edge k+1. The block also has exactly 2 stages (operands registered at edge k, result at edge k+1), so a block fed combinationally from the module inputs lines up edge-for-edge with the original.

Chaining is not usable here: a chained pair needs 3 edges from the first block's operands to the second block's result, which would put r one cycle late, and the data cannot be started a cycle earlier because it comes straight from the module's inputs. So the third product of each colour gets its own block and the two block results are added outside. That outside adder is only 7 bits wide: r is 7 bits, the original sum is evaluated in 15 bits and then truncated, and (x+y) mod 2^15 mod 2^7 = (x+y) mod 2^7, so the low 7 bits of the two result ports are all that is needed.

Products are exact in both: ul*rul ≤ 255·127 = 32385 < 2^15, so the original 15-bit product never wraps, and the block's 37-bit unsigned product is the same value. All operands are unsigned regs/inputs, matching the block's unsigned reading; ax/ay zero-extension matches the original's zero-extension into the 15-bit context.
